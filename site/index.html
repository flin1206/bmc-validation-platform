OpenBMC · firmware validation · test infrastructureOpenBMC · 韌體驗證 · 測試基礎設施

Validating the computer that controls the computer. 驗證那台掌控伺服器的電腦。

A BMC can power a server off, reflash it, and is reachable over the network. This project boots real OpenBMC firmware in QEMU (including the BMC of an NVIDIA GB200 NVL rack), tests it over Redfish and IPMI, gates every build on the vulnerabilities it introduces, and checks the GPUs it manages, all from one Jenkins pipeline. BMC 可以把伺服器關機、重刷韌體，而且接在網路上。這個專案把真實的 OpenBMC 韌體放進 QEMU 開機（包括 NVIDIA GB200 NVL 機櫃的 BMC），透過 Redfish 和 IPMI 測試它，依每個 build 新增的漏洞決定能不能出貨，也檢查它所管理的 GPU，全部串在同一條 Jenkins pipeline 裡。

§1Scope範圍

Three questions every firmware build has to answer每個韌體 build 都必須回答的三個問題

FUNCTIONAL

Does it behave correctly?行為正確嗎？

71 pytest cases over Redfish and IPMI, run against the booted image: sensors, power, RBAC, malformed input, rejected firmware updates.對開機後的映像執行 71 個 Redfish 與 IPMI 測試：感測器、電源、RBAC、異常輸入、被拒絕的韌體更新。

SECURITY

Did this build make it less secure?這次 build 有沒有變得更不安全？

SBOM, then Grype, then a diff against the last good build. Only new findings fail the gate. Waivers need an owner and an expiry date.SBOM → Grype → 與上一個通過的 build 比較。只有新增的漏洞會讓 gate 失敗；豁免必須有負責人和到期日。

DIAGNOSTICS

Is the node healthy?節點健康嗎？

A C++/NVML health tool, DCGM diagnostics and Xid log triage decide whether a GPU node should be reset, drained or trusted.C++/NVML 健康檢查、DCGM 診斷和 Xid log 分診，判斷 GPU 節點該重置、下線，還是可以信任。

§3Finding發現

56% of the “firmware vulnerabilities” were in software that never ships56% 的「韌體漏洞」，其實在根本不會出貨的軟體上

Yocto's image SPDX also describes the tools on the build machine, such as rsync-native and openssl-native. OpenBMC ships no package database, so scanning the rootfs alone sees almost nothing. The gate scans the SPDX and then keeps only packages listed in the image manifest. Every exclusion is printed in the report so a reviewer can audit the filter.Yocto 的映像 SPDX 也把建置機器上的工具寫進去了，例如 rsync-native、openssl-native。OpenBMC 又沒有附套件資料庫，只掃 rootfs 幾乎什麼都看不到。所以 gate 先掃 SPDX，再只保留映像 manifest 裡列出的套件，而且每一筆排除都印在報告上，讓審查者檢查過濾是否正確。

§6Coverage覆蓋範圍

Negative tests assert three things負向測試同時檢查三件事

Each test checks the right status code, a spec-compliant Redfish error body with the exact MessageId, and that the BMC is still alive afterwards. A rejected firmware image only passes if the running version is unchanged.正確的狀態碼、符合規格且 MessageId 正確的 Redfish 錯誤內容，以及測完之後 BMC 還活著。被拒絕的韌體映像，只有在執行中的版本沒變時才算通過。

§8Decisions設計決策

Choices that keep the signal trustworthy讓結果值得信任的設計選擇

  • D2Fresh flash copy every boot每次開機都用全新的 flash 複本

    The emulated flash is writable. Without a copy, a test that flashes firmware leaks state into the next run, and failures start depending on test order.模擬的 flash 可寫。不複製的話，刷韌體的測試會把狀態留給下一輪，失敗結果會取決於測試順序。

  • D4Ready means usable, not listening就緒是指可以用，不是有在聽

    bmcweb answers the service root before its D-Bus backends are up. Readiness requires a real session and a populated Managers collection.bmcweb 在 D-Bus 後端啟動前就會回應 service root。就緒必須能建立真的 session，而且 Managers collection 已有成員。

  • D6Retry connections, never HTTP errors重試連線錯誤，絕不重試 HTTP 錯誤

    Retries cover a BMC that is rebooting. They never cover a 500, so a flaky endpoint can't hide behind a retry.重試是為了應付正在重開機的 BMC，不處理 500，所以不穩定的 endpoint 無法靠重試蒙混過去。

  • D9Loopback-only port forwardsPort forwarding 只綁 loopback

    The emulated BMC uses the well-known default password, so it must never be reachable from the lab network. A unit test enforces this.模擬的 BMC 使用眾所周知的預設密碼，絕不能從實驗室網路連得到。這點由單元測試把關。
